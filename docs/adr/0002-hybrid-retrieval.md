# ADR 0002: Hybrid retrieval (BM25 + dense, fused with RRF)

Status: accepted (design decision taken before any measurement; the later golden-set ablation
shows hybrid level with dense-only, not better; see "Evidence")

## Context

The corpus is 41 pages of Python 3.12 standard-library documentation (ADR 0001). Questions
about it mix two kinds of signal:

- exact identifiers (`bisect_left`, `shutil.copy2`, `secrets.token_hex`, `ZIP_DEFLATED`) that
  a lexical index matches directly and an embedding model may blur;
- paraphrased intent ("how do I merge sorted inputs lazily") that shares few words with the
  page and needs semantic similarity.

Everything had to run locally and free, with no server beyond the model server, and the
retrieval stage had to be deterministic so that recorded runs replay exactly in CI (ADR 0004).

## Decision

Retrieve with two indexes and fuse their rankings:

- **Keyword:** SQLite FTS5 with BM25 and the `porter unicode61` tokenizer
  (`src/evalrag/retrieval/keyword.py`). The query is reduced to its word tokens, each quoted
  and joined by `OR`, so user text cannot inject FTS5 syntax.
- **Dense:** cosine similarity over `nomic-embed-text-v1.5` vectors held in a NumPy matrix and
  persisted as `.npz` (`src/evalrag/retrieval/dense.py`). Scores are rounded to 6 places and
  ties broken by chunk id, so the order is deterministic.
- **Fusion:** reciprocal rank fusion, `score = sum(1 / (60 + rank))` over the two lists of the
  top 50 candidates each (`src/evalrag/retrieval/fusion.py`, `hybrid.py`), ties broken by
  chunk id. The top `k` (3, ADR 0005) fused chunks go to the model.
- The dense rank-1 cosine, taken before fusion, is kept as the retrieval-confidence signal for
  abstention (ADR 0006).
- An optional reranker hook exists in `HybridRetriever` but is unused by default.

## Consequences

- No vector database or search server: two files on disk plus a chunk table, built by
  `evalrag ingest` in seconds from recorded embeddings.
- RRF needs no score calibration between BM25 (unbounded) and cosine (bounded), which is why
  it was chosen over a weighted score sum. The cost is that fused scores carry no confidence,
  so abstention uses the dense cosine instead (ADR 0006).
- Every query pays for an FTS5 search and a full dense scan. At 1289 chunks this is
  negligible; it would not scale to millions of chunks without an approximate index.

## Evidence

`evals/reports/retrieval-ablation.md` (generated by `evals/analysis/retrieval_ablation.py`,
replayed offline from the committed embeddings, checked byte for byte by
`tests/acceptance/test_retrieval_ablation.py`) scores the three options on the 50 answerable
golden items at document level, with the harness's own metric functions:

| Retriever | recall@1 | recall@3 | recall@5 | MRR (top 3) | items with recall@3 = 0 |
| --- | --- | --- | --- | --- | --- |
| keyword-only (FTS5 BM25) | 0.6700 | 0.8200 | 0.8500 | 0.7900 | 7 |
| dense-only (cosine) | 0.8100 | 0.8800 | 0.9000 | 0.9133 | 3 |
| hybrid RRF k=60, no guard (shipped) | 0.8000 | 0.8800 | 0.9000 | 0.8967 | 4 |

The hybrid row equals the harness's published golden `recall_at_k` (0.88) and `mrr` (0.8967),
which the tests check.

What it shows:

- Keyword-only is the weakest option on every column.
- Hybrid is level with dense-only on recall@3 and recall@5 and slightly behind on recall@1
  (0.80 against 0.81) and MRR (0.8967 against 0.9133). Hybrid recovers one item dense-only
  misses (g011) and loses two that dense-only finds (g016, g032).
- So on this set, fusing BM25 in did **not** improve document-level retrieval over dense-only.

What it does not show:

- That dense-only is better: the gaps are one or two items on a 50-item, single-author set.
  One single-document item moves a recall by 0.02.
- Anything about passage-level precision: a chunk from the right page counts even if it does
  not contain the answer.
- Anything about other embedding models, chunk sizes, RRF constants or candidate depths; none
  was varied.
- The golden set was used here for measurement only. The design was not changed because of
  this result, and switching to dense-only on the strength of it would be tuning on the
  held-out set.

## Rejected

- **Dense-only.** It was the main alternative at design time, rejected for the identifier
  argument above. The ablation now shows it level with hybrid on this set, so this rejection
  rests on the design argument, not on measured benefit. Revisiting it needs a new held-out set.
- **Keyword-only (BM25).** Simplest and fully deterministic without an embedding model, but it
  misses paraphrased questions. Measured: weakest on every column (recall@3 0.82, MRR 0.79).
- **Weighted sum of normalised scores.** Needs a per-query normalisation of unbounded BM25
  scores and a tuned weight; RRF needs neither.
- **A cross-encoder reranker by default.** Another model to serve and record, more latency on
  CPU, and retrieval was not the bottleneck (recall@3 0.88; generation is the weak part, see
  `evals/reports/golden-failure-analysis.md`). The hook stays available.
- **A vector database server** (for example Qdrant, Chroma, pgvector). Unneeded at 1289 chunks
  and one more service to run in CI and Docker (see ADR 0003).

## Limitations

- RRF k=60 and the candidate depth 50 are standard defaults, not tuned values.
- Dense scoring is an exact scan, fine at this size only.
- The keyword query ORs all tokens, so common words add noise; there is no stop-word list.
